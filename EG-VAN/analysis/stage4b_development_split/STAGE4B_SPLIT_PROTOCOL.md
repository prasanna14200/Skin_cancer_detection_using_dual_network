# Stage 4B prospective internal development split protocol (version 1)

**Frozen before generating any Stage 4B membership file.** Purpose: an exploratory, lesion-disjoint internal selection boundary for two **freshly initialized** models only. It is not an untouched evaluation of the existing frozen Stage 23 checkpoint. No original data, archived split, checkpoint or historical outcome is to be changed.

## Eligible pool and deterministic assignment

- Input is solely rows marked `train` in `data/splits/split_leakage_aware.csv`, SHA256 `f1c04c5ef5b54372c667daf0aebc29e6f24743c6c2cc094f16e2c4e679149883`. Expected: 8,015 unique image IDs from 5,973 lesions. Never import original `val`/`test`, the naive split or PH2 into either output manifest. Check every lesion has one diagnosis and every image has raw and processed JPEG files.
- Seed: literal UTF-8 string `20261010`; class order `akiec,bcc,bkl,df,mel,nv,vasc`. Within each class, compute SHA256 of `stage4b-v1|20261010|<class>|<lesion_id>` encoded as UTF-8. Sort lesions by `(digest, lesion_id)` ascending. The first `floor(0.20 × number_of_class_lesions + 0.5)` lesions become **internal_selection**; all others become **development_train**. Abort if the count for any class would leave either role empty. This stable hash sort avoids dependency on NumPy or Python RNG versions. Every image from a lesion inherits exactly one role.
- The selection fraction is 20% of **lesions within each class**, not a guarantee of 20% of images. Report both lesion and image counts by class after assignment. IDs in each CSV are sorted lexicographically by `image_id`. There is no result-driven rebalancing or exception after assignment.
- Stage 4B may read original split membership solely to verify isolation. It must not read original validation/test predictions, PH2 predictions, uncertainty outcomes or any model metric while assigning membership. Stage 4A's prior scientific hypothesis choice is documented separately; no held-out outcomes choose membership.

## Versioned artifacts and checks

Create `stage4b_development_train_v1.csv` and `stage4b_internal_selection_v1.csv` with `image_id,lesion_id,dx,original_split,stage4b_role,raw_image_sha256,processed_image_sha256`. SHA256 is over the exact bytes of each canonical `data/raw/images/<image_id>.jpg` and frozen `data/processed/images/<image_id>.jpg`. Create `stage4b_split_manifest_v1.json` last, containing schema/algorithm, source-file hashes, both CSV hashes, counts, class distributions, duplicate and near-duplicate screening summary, and limitation flags. Never overwrite an existing Stage 4B file; a change in source bytes, algorithm, seed or inclusion rules requires a new version and a new prospective rationale.

Before assigning a readiness status, verify all 8,015 original train IDs appear exactly once across the proposed CSVs; no original validation/test ID or lesion occurs; each role includes all seven classes and melanoma image/lesion counts are reported; no original exact-byte duplicate pair crosses roles; and every generated hash matches current bytes. Hash all 8,015 canonical raw and processed JPEGs. Screening for possible **near duplicates** uses a 64-bit horizontal difference hash (grayscale raw image reduced to 9×8; adjacent horizontal intensity comparisons) and Hamming distance ≤4 **across roles and different lesion IDs**. This is a candidate screen, not a proof of identity or of absence of other near duplicates. Any flagged cross-role pair requires blinded manual resolution before a training authorization. Lack of patient IDs remains an explicit limitation.

No Stage 23 weights are loaded or evaluated on the proposed holdout. The conditional comparison, checkpoint selection, metrics and stopping rules are in `FRESH_CONTROL_VS_TREATMENT_PROTOCOL.md`; generating this split does **not** authorize training.
